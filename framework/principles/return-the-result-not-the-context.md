# Return the Result, Not the Context

**Origin:** Scoped subagent design
**Applies to:** Any content crossing a scope boundary — child agent
to parent, session to stored memory

## Principle

When work crosses a boundary, the result crosses. The context does
not.

A child agent reads its source material; the parent receives the
conclusion. That is how delegation works between people, and it is
the only version where merging does not defeat the point of scoping.
If a parent absorbs its children's context, scope ratchets upward
and every delegation ends with a broader agent than it started with.

Two rules:

1. **Return the result, not the context.**
2. **Same-persona merges only.** A child running under a different
   persona reports completion and nothing else. A summary does not
   launder the boundary — derived content still carries what it was
   derived from.

## Corollaries

**Write-back to storage and child-to-parent merge are the same
operation.** Both are content crossing a boundary. One gate, not two.

**Acceptance criteria are the merge gate.** Work that fails its
criteria returns nothing and reports failure. No partial merge, no
unvalidated content entering the parent.

**Acceptance criteria bound the output, not the process.** An agent
can exceed its scope, take actions in the world, and still return
something that passes its criteria. Pair criteria with a declared
action budget stating what the agent may read, write, and call.
Criteria are a filter at the end; the action budget is the constraint
throughout.

**The action budget states what may not be repaired, not only what may
not be touched.** An agent that finds a defect outside its declared
intent reports it and completes its intent. It does not fix it.

> **Why:** silent repair is the scope violation that produces a
> *passing* result, which is exactly why acceptance criteria cannot
> catch it. A capable agent that quietly improves what it was told to
> copy returns better work and a worse system — an unrecorded change
> living in one copy while the source it came from stays behind. The
> danger is not a bad output. It is a good output from an unauthorized
> action, and only the budget can forbid it.
>
> A builder told to install something verbatim and report rather than
> fix turns every defect it finds into a tracked correction upstream,
> where fixing one often surfaces the next. A free hand turns the same
> defects into silent forks, one per fix, that nobody upstream knows
> about.

**The action budget binds the dispatcher, not only the agent.** An
instruction can transfer authority as a side effect. Before dispatching
work, state what the instruction *grants* alongside what it *asks for*,
and check whether carrying it out moves any boundary that was not
named.

> **Why:** constraints that bind only the agent get broken by the party
> writing them, in a task that otherwise looks correct. Acceptance
> criteria cannot catch it, because the dispatched work succeeds — the
> damage is in a side effect nobody specified.
>
> Example: a tool that records ownership by use — whatever it pushes,
> it may later delete. Tell a builder using that tool to push a file it
> was never meant to own, and the dispatch is otherwise correct while
> the transfer of delete rights is invisible in it. Authority accrues
> through use unless it is declared, which is the inverse of an
> authority model keyed on file location, and fails the same way.


**Criteria for named intents are authored in the manifest and
human-reviewed.** A model that writes its own acceptance criteria can
write criteria it knows it will meet.

**Agent unpredictability is partly a specification failure.** An
agent with no defined done-state does not stop. Criteria bound the
search. This does not make an agent safe on its own — see the action
budget above — but an unspecified outcome guarantees an unpredictable
one.

## How to tell if this is being violated

- A parent's context is larger after delegation than before
- A summary is used to move content that a direct read would not have
  been permitted to move
- An agent reports success and the reviewer cannot state what "done"
  was
- Unpredictability is blamed on the agent when no done-state was ever
  specified
- Acceptance criteria were generated by the same model that had to
  meet them
- An agent improved something it was asked to copy, and the improvement
  is visible only in the copy
- An instruction moved a boundary the instruction never mentioned
- Only the dispatched agent's actions were budgeted, and the
  dispatcher's were not

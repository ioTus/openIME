# GitHub Sync Utility — Reference

Replit Agent cannot `git push` — the platform blocks outbound
git protocol traffic. The automated sync utility replaces all
git push/pull operations with GitHub API calls.

## The canonical implementation

**`scripts/github-sync.ts` in the GitBridge MCP repository** is the
canonical, repo-agnostic sync utility, copied into every new spoke during
onboarding (Phase 1 of `spoke-setup.md`).

**Check the version record in `framework/maintenance.md` §Distributed
asset discipline before copying it.** The canonical path is not
guaranteed to hold the newest version; the copy to take is named in
that record.

The behaviour documented below describes the current best version, not
necessarily the file at the canonical path.

## What it does

1. Reads `ime.config.json` for owner/repo/branch
2. Detects all local changes (tracked and untracked)
3. Reads GitHub's current HEAD via the Git Data API
4. Compares upstream changes against local changes — flags
   overlap with warnings (last-writer-wins, but warns)
5. Detects deleted files via the sync manifest (see below)
6. Creates a new tree, commit, and updates the ref — single
   atomic commit including additions, modifications, and deletions
7. Updates the sync manifest after commit
8. Verifies the push landed (SHA comparison)
9. Reports results with commit SHA, file list, and warnings

## Deletion tracking — the sync manifest

### The problem

The sync utility pushes files to GitHub via the Git Data API.
Without deletion tracking, renamed or removed files leave ghost
paths on GitHub indefinitely. A naive deletion approach (compare
GitHub tree against local filesystem) is dangerous in a
multi-agent setup because Claude pushes files to the same repo
that only exist on GitHub, never locally on Replit. Deleting
"anything on GitHub that isn't local" would silently destroy
Claude's plan docs, specs, and governance files.

### The solution: `.replit-sync-manifest.json`

The sync utility maintains a manifest file that tracks every
path Replit has pushed to GitHub. This is the ownership record.

**How it works:**

1. After each successful sync, the manifest is updated with
   every path Replit pushed (new paths added, existing retained)
2. On each sync cycle, the manifest is compared against the
   local filesystem
3. Any path in the manifest that no longer exists locally =
   Replit deleted or renamed it → included as a `sha: null`
   deletion in the GitHub tree
4. Deleted paths are removed from the manifest after commit
5. The manifest update is included in the same commit as the
   file changes (atomic)

**Why this is safe:**

- Only tracks files Replit explicitly pushed — never touches
  Claude's files, manual pushes, or anything Replit didn't create
- No dependency on git commands (no `index.lock` risk)
- No directory-level config to misconfigure
- No false positives from diverged git history
- Deterministic: the manifest is the source of truth for what
  Replit owns on GitHub

**Defensive defaults:**

- Missing manifest = treat as empty. Never delete on incomplete
  information. Rebuild from the current push forward.
- Path in manifest but already gone from GitHub = skip silently,
  remove from manifest. No error.
- Manifest write failure = do not delete anything on this cycle.
  The default is always "if unsure, don't delete."

### Manifest file location

`.replit-sync-manifest.json` at repo root. It is committed to
GitHub (not local-only) so it survives Replit session restarts.
Do not add it to `.gitignore`.

## Required files per project

| File | Purpose |
|------|---------|
| `scripts/github-sync.ts` | The sync utility. Copy from the version named in `framework/maintenance.md` §Distributed asset discipline — not from a remembered path. |
| `scripts/test-github-sync.ts` | Regression coverage. Part of the asset, distributed with it — copy both together. |

The builder also adds a `test:github-sync` package script. That file is
builder-owned, so it is requested rather than scaffolded.

## Authentication

Uses the Replit GitHub integration (connectors SDK) as primary.
Falls back to `GITHUB_PERSONAL_ACCESS_TOKEN` env var if the
integration isn't available. The Replit GitHub integration must
be set up during onboarding (Phase 2 of `spoke-setup.md`).

## Usage

### Push changes

```bash
npx tsx scripts/github-sync.ts "[commit message]"
```

### Post an issue comment

```bash
npx tsx scripts/github-sync.ts comment <issueNumber> "<comment body>"
```

Example:
```bash
npx tsx scripts/github-sync.ts comment 1 "**[Replit]:** Build complete. SHA: abc123"
```

This subcommand exists because Replit Agent's JavaScript sandbox
is not always available (e.g., in Lite mode). The CLI path ensures
issue comments can always be posted regardless of the agent's
execution context.

### Programmatic usage

```typescript
import { syncToGitHub, commentOnIssue } from "./scripts/github-sync";

const result = await syncToGitHub("[feat] add new feature");
if (result.success) {
  console.log(`Pushed: ${result.sha}`);
  await commentOnIssue(1, `Pushed: ${result.sha}`);
}
```

## Critical rule

Replit Agent must use this utility after every unit of work.
Never use `git push`, `git pull`, `git fetch`, or the Git panel
for syncing. This is the only path that works on Replit's platform.

## Design history

The utility began as a manual Git Data API protocol, was automated,
then gained manifest-based deletion tracking so a multi-agent repo
where two agents write files could delete safely, and finally the
`comment` subcommand so issue comments work where the programmatic
API is unavailable.
